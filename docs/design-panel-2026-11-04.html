0. Understanding (write-back)

Goal: replace imdinu/apple-mail-mcp 0.5.0 in the opencode mail agent with an own MCP server that (a) returns To/Cc, (b) decrypts S/MIME mail with the user's own certificate, (c) starts and answers fast with low friction, (d) others can use, (e) gets a fitting name and is published under the Glia GitHub organisation.

Constraints: Claude never reads real mail during implementation; tests run on synthetic data; real-store checks only via opencode Qwen sessions or anonymised output (counts, booleans, hashes). Read-only stays enforced (no send/move/flag/delete).

assumed Assumed (please correct): encryption means S/MIME (one valid S/MIME identity found in the login keychain), not PGP. The opencode mail agent prompt and the mail_* permission rules should keep working with minimal edits. The Google account stays excluded. Apple Mail remains the only mail client of record (Exchange/EWS accounts are out of scope: they keep no local files).

Success looks like: a Qwen session answers "who was CC'd on X?" and "what does the encrypted mail from Y say?" correctly; server up in well under a second; no index to rebuild, no lock to fight; a stranger can uvx <name> and add two lines to an MCP config.

1. What is wrong today (evidence)

apple-mail-mcp 0.5.0 (GPL-3, Python, fastmcp 3 beta):

  • Parses only Subject, From, Received, Date, Reply-To, Message-ID from each .emlx. To/Cc/Bcc are never read and never stored; the Envelope Index recipients table is never queried. PR #129 adds to/cc to get_email only, still open since 2026-10-07.
  • Builds its own copy of every message body into ~/.apple-mail-mcp/index.db (FTS5). That copy is what goes stale: --watch depends on FSEvents and on Full Disk Access of whichever process holds the writer lock; issues #122/#130 report days of staleness and starved instances; #125 reports one bad .emlx aborting the whole sync. On this Mac the index silently went stale on 2026-10-30 after a Glia rebuild changed the TCC grant.
  • application/pkcs7-mime bodies are base64-decoded and UTF-8-decoded with errors=replace: ciphertext becomes mojibake, and that mojibake is written into the FTS index.
  • Account names via JXA (osascript), which needs the Automation→Mail grant, the second TCC grant the README fights with.
  • fastmcp import alone costs ~2 s (their PR #117 measurement).
  • --read-only disables nothing in 0.5.0 (no write tools exist; _ensure_writable is dead code).

2. Decisions

D1Name

Themes: the envelope (From/To/Cc is literally the envelope; Apple calls its database "Envelope Index"), the letter opener (opens sealed mail, never writes), the seal (S/MIME).

Rejected: envelope (taken everywhere), paperknife (1.5k-star PDF tool), letter-opener (brew cask + npm), unseal (taken), postbox (commercial mail client), lettre (Rust mailer).

Recommendation

paper-knife. Tagline: "a letter opener for Apple Mail: read-only MCP server with full envelopes and S/MIME". The opencode server key stays mail, so tools keep appearing as mail_*.

Facts used: recipients(message, address, type 0=To 1=Cc 2=Bcc, position) joins addresses(address, comment); subjects.subject lacks the "Re:" prefix which sits in messages.subject_prefix; timestamps on macOS 26 are plain Unix seconds (detected, not assumed); summaries holds a preview for a minority of messages; ROWIDs change when Mail rebuilds the index, so get_email also returns the RFC Message-ID header.

Recommendation

live read-only Envelope Index, schema resolved by PRAGMA table_info at startup. Snapshot copy only as a fallback if the read-only open fails.

D4Body text search

Header search (subject, from, to, cc, date, mailbox) is instant from the Envelope Index. Body text is not in that database (Spotlight does not index Mail since macOS 10.15; confirmed 0 results here). Three ways:

Encrypted bodies are never indexed in any option.

Recommendation

A in phase 1; B as phase 2 only if A's bounded scans prove too slow for real usage. The current agent prompt already steers Qwen to sender/subject scopes and date windows, which A serves instantly.

D5S/MIME decryption

How Mail finds the key: Mail (bundle id com.apple.mail) may use the iCloud/data-protection keychain; every other process, including /usr/bin/security and any own binary, searches only the legacy file keychains (login.keychain-db). This Mac: security find-identity -v -p smime reports 1 valid identity in the file keychain, so the key is reachable.

Nesting to handle: enveloped-data → (opaque signed-data or multipart/signed) → multipart/alternative|mixed. Signed-only mail passes through today and stays that way; signature status is reported, not enforced.

Plaintext policy: decrypt on demand in get_email; never write plaintext to disk; no in-memory cache beyond the one response. Search over encrypted bodies: not offered (headers and subject still searchable). The doctor command runs one real decrypt with -n (content suppressed) and reports only ok/fail, so the keychain path gets verified on this Mac without anyone reading the message.

Recommendation

A, with C documented as the portable fallback for people whose key is not in a macOS keychain. First real-keychain check happens in doctor, run by the user.

D6Account names and exclusion

Mailbox URLs in the Envelope Index look like imap://user%40host@host/INBOX; user and host identify the account without JXA. Excluding an account becomes a config pattern on user/host. This removes the Automation→Mail grant entirely; only Full Disk Access remains, and it is charged to the app that launches opencode (Glia), as before.

Recommendation

derive accounts from mailbox URLs; no osascript anywhere in the code.

Proposed

Dropped: get_email_links, get_email_attachment (writes files to disk), the index://status resource. Added CLI (not MCP): doctor [--anon].

D8Code reuse

mailgrep (hexrw, MIT, zero dependencies, 118 tests on synthetic fixtures) already implements: schema introspection, epoch detection, subject-prefix join, recipients subquery, emlx parsing incl. the single-dash boundary repair, the four attachment states, FDA error disambiguation, and a synthetic store generator. apple-mail-mcp is GPL-3: ideas only, no code.

Recommendation

copy the needed mailgrep modules into the new package under its own module names, with the MIT notice kept. Reasons: no PyPI release of mailgrep exists to depend on; and its CLI stays off PATH.

D9Distribution and the Glia question

Proposed
  • Git repo + PyPI package, so uvx paper-knife works; MIT licence.
  • opencode: "command": ["uvx", "paper-knife"] under the existing mail key; the agent file and permission map stay unchanged.
  • Claude Code / Claude Desktop: the same one-liner in their MCP config (FDA is charged to the launching app).
  • "Publish through the Glia workspace": the glia CLI has only show, jail, help, version; nothing publishes. Open question Q1.

D10Read-only guarantee

Proposed

By construction: no AppleScript, no IMAP, no write path, SQLite opened mode=ro, nothing written outside ~/.cache/<name> (phase 2 only). A test greps the source for write verbs (send, move, delete, flag, osascript). No --read-only flag, because there is nothing it could switch off.

4. Verification without reading mail

  1. Synthetic store: a generator builds a fake ~/Library/Mail/V10 tree with an Envelope Index (messages, subjects, addresses, recipients, mailboxes, summaries), .emlx and .partial.emlx files covering the four attachment states, an S/MIME encrypted+signed message produced with a throwaway OpenSSL cert, and mixed epochs. All unit and MCP protocol tests run against it, with a stdio client calling every tool.
  2. Decrypt path: automated tests use the OpenSSL fallback (C) with the throwaway key. The keychain path (A) is checked by doctor on the real Mac: one message, -n, exit code only.
  3. Real store, anonymised: doctor --anon prints only counts, schema resolution, detected epoch, FDA status, identity found yes/no, decrypt probe ok/fail, and timing. That is the only real-store output Claude sees.
  4. opencode Qwen smoke test: a scripted session with the mail agent is told to answer with booleans and counts only ("did get_email return a non-empty cc list: yes/no"). opencode run hangs intermittently on this machine, so the harness uses opencode api against the running service, with a timeout.
  5. Timing: startup, search and get_email latency on the real store, reported as numbers.
